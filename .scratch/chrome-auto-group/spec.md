# 自动标签页分组扩展

Status: ready-for-agent

## 问题陈述

用户打开许多来自不同网站的标签页后，需要手动整理标签组。过去使用的类似扩展可能在 Chrome 启动时卡顿；本扩展需要避免全量启动扫描和任何同步或持久化状态，同时能按域名直觉自动组织标签页。

## 解决方案

提供一个轻量的 Chrome 扩展，根据普通网页 hostname 中的域名标签推断小写网站标识，并在每个浏览器窗口内自动创建或复用同名标签组。已分组标签页跨站导航时按已确认的标题规则换组；手动分组受到尊重。用户可显式整理当前窗口中仍未分组的网页标签页。扩展不持久化标签状态或规则，也不联网；仅在 session 内存中暂存新建标签页等待首次网页地址的待处理标记。

## 用户故事

1. 作为 Chrome 用户，我希望打开 Google、Bing、YouTube 等网站时标签页自动进入对应网站标识的分组，以便减少手动整理。
2. 作为 Chrome 用户，我希望网站标识统一使用小写，以便同一网站不会因为大小写差异形成多个组。
3. 作为 Chrome 用户，我希望 `www.google.com`、`mail.google.com` 等包含已知网站标签的地址识别为 `google`，以便常见子域名归入同一组。
4. 作为 Chrome 用户，我希望识别按 `.` 分割后的完整标签进行，而非任意文本包含，以便 `notgoogle.com` 识别为 `notgoogle`。
5. 作为 Chrome 用户，我希望 `google.example.com` 能根据内置名称标签识别为 `google`，以便 hostname 中明确出现的已知网站标识可以命中。
6. 作为 Chrome 用户，我希望 `youtu.be` 不被特例映射为 `youtube`，而是在没有已知标签命中时按默认规则得到 `youtu`，以便内置表只维护名称标签而不维护域名映射。
7. 作为 Chrome 用户，我希望未知域名仍能按注册域名主体生成分组标识，以便扩展对内置表之外的网站也有用。
8. 作为 Chrome 用户，我希望 hostname 同时含有多个内置网站名称时，选择离注册域名主体最近的命中标签，以便匹配结果稳定且可预测。
9. 作为 Chrome 用户，我希望普通 HTTP/HTTPS 网页会自动分组，而 Chrome 内部页面、扩展页面、本地文件等不参与处理，以免扩展影响特殊页面。
10. 作为 Chrome 用户，我希望同一窗口中相同网站的标签页加入同一个标签组，以便标签页聚合在一起。
11. 作为 Chrome 用户，我希望不同窗口各自拥有自己的同名网站组，以便窗口间保持独立。
12. 作为 Chrome 用户，我希望已有标签页跨网站导航后能移入新网站对应的组，以便标签组跟随标签页当前访问的网站。
13. 作为 Chrome 用户，我希望导航后的标签页若处于名称无法由网站识别规则识别的手动组中，就继续留在该组，以便保留我的手动安排。
14. 作为 Chrome 用户，我接受名称恰好等于可识别网站标识的手动组可能被视为自动组，以便扩展在不记录分组来源的前提下仍能处理常见跨站导航。
15. 作为 Chrome 用户，我希望 Chrome 启动时扩展不枚举并重整所有已有标签页，以便避免启动卡顿。
16. 作为 Chrome 用户，我希望可以主动整理当前窗口尚未分组的普通网页标签页，以便需要时整理已有页面，同时不打乱已有分组。
17. 作为注重隐私的用户，我希望扩展不持久化标签页状态、规则或偏好，也不进行云同步或网络请求，以便浏览数据留在浏览器本机且扩展保持轻量；允许仅在 session 内存中暂存待处理标签 ID，以覆盖空白页等待期间 worker 休眠的情况。
18. 作为扩展开发者，我希望产物可在 Chrome 中加载并打包提交到 Chrome Web Store，以便完成后能够自行发布。

## 实现决策

- 扩展采用 Manifest V3；后台行为由事件驱动，不在启动时查询所有窗口和标签页。
- 代码内置常见网站名称标签列表，例如 `google`、`bing`、`youtube`。列表只保存网站名称标签，不维护 hostname 到名称的映射；不支持用户编辑规则，也不联网更新列表。
- hostname 转小写并按 `.` 分割。排除 `www` 和公共后缀标签；先检查注册域名主体是否命中内置列表，再检查 hostname 的其他标签。多个其他标签命中时，选择离注册域名主体最近的一个。
- 没有内置名称命中时，使用注册域名主体作为默认网站标识。公共后缀识别使用随代码发布的小型常见多段后缀表。
- 新建且未分组的普通网页标签页依据网站标识创建或加入当前窗口内的同名标签组。
- 对已分组标签页的 URL 变化，仅当当前组标题与识别规则可产生的网站标识一致时才按新 URL 换组；其他组名视作用户手动安排并保持不动。若用户手动创建的组名恰好与有效网站标识相同，扩展无法区分其来源，按自动组处理。
- 每个窗口独立查找和复用标签组。标签组标题使用小写网站标识。
- 扩展不使用磁盘持久化存储或同步，不保存组 ID、浏览记录、规则、偏好或分组来源；分组标题是判断标签组归属的唯一依据。仅允许用 `chrome.storage.session` 在浏览器内存中暂存新建标签页等待首次网页地址的待处理标记（标签 ID），在分组、手动入组或关闭后删除，浏览器重启或扩展重新加载时清除；不得将网址或历史写入该存储。
- 扩展提供一个“整理当前窗口”入口；该操作只处理尚未分组的普通网页标签页，保留全部已有分组。
- 普通网页之外的地址不参与自动分组或手动整理。
- 交付物应能本地加载并生成可提交到 Chrome Web Store 的扩展包；本规格不授权实际发布。

## 测试决策

- 只通过用户可观察行为验证，不测试内部函数拆分、存储实现或事件监听器数量。
- 建立一个 Chrome 扩展行为测试 seam：加载扩展，通过标签页创建、导航及工具栏整理操作驱动行为，并检查 Chrome 原生标签组标题、标签页成员关系和窗口隔离。
- 场景应覆盖：已知名称标签、未知域名默认标识、多标签命中顺序、特殊 URL 跳过、创建/复用分组、跨站导航、普通手动组保留、同名组歧义、窗口隔离、启动不全量整理、空白新标签页跨 worker 休眠后首次导航仍会分组，以及手动整理仅处理未分组页。
- 当前仓库没有实现代码或测试先例；此行为测试 seam 需要新建，优先保持为一套浏览器级测试，不另建内部识别逻辑测试层。

## 范围之外

- 用户自定义、导入或编辑识别规则。
- Chrome Sync、云端服务、账号、网络请求、浏览历史或标签状态持久化。
- 启动时扫描并自动整理恢复的全部标签页。
- 识别网页内容、页面标题、搜索词或网站内容脚本注入。
- 合并不同浏览器窗口中的标签组。
- 真实 Chrome Web Store 上架操作、开发者账号操作及商店页面素材制作。

## 补充说明

- 领域术语遵循项目 `GLOSSARY.md`，状态及无持久化决定遵循 ADR-0001。
- 首版内置网站标签表的具体条目由实现时确定，至少包含 `google`、`bing`、`youtube`；新增条目只需名称标签，不添加域名映射。
- 自动分组识别和跨站跳转处理只基于地址栏 hostname，不读取网页内容。
- 2026-10-17 用户确认允许上述 session 内存待处理标记；这是对原先“不保存标签 ID”的有限修订，原因见 ADR-0001。
